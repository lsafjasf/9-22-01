# 故障恢复与只读取证流程

系统对“进程被 `kill -9`、消息丢失/重复/迟到/乱序、网络分区”是自动恢复的；
唯独**协调者（或参与方）日志本身损坏**时不允许程序猜测，必须由人根据证据
决策。取证工具 `two_phase_commit.cli inspect` 全程只读。

## 1. 自动恢复能处理的情况

- 协调者在任意时刻被强杀，重启后重放日志：已有决议则重放并补发，无决议
  则推定中止（见 `state_machine.md` 第 3 节）。
- 参与方在投票后、收决议前崩溃：恢复为 PREPARED 并周期 `STATUS_QUERY`。
- 参与方在 APPLY fsync 后、ACK 发出前崩溃：重启后不会重复执行效果，只
  重发 ACK。
- 决议消息丢失/重复/乱序：协调者与参与方双方定时重试 + 幂等处理。
- 阶段 2 网络分区：分区愈合后由重试/查询收敛；决议不变。

程序在启动重放时若发现 CRC 错误或撕裂帧，会**拒绝启动**并提示使用
`inspect`，而不是截断尾部继续运行——因为损坏帧之前的可读前缀是唯一可信
证据，损坏帧的内容不可推断。

## 2. 取证工具的证据与建议决议

`inspect` 读取一个目录（约定 `coordinator.log` 与
`participant-*.log`）或显式给出的日志文件列表，对每个事务输出：

- `recommendation`：建议决议；
- `safe`：是否可安全地按建议执行（`false` 表示必须人工介入）；
- 证据清单（谁有 `DECISION` / `APPLY`、谁的日志撕裂、谁的日志缺失）；
- 阻塞 / 已提交 / 已回滚的参与方列表；
- 建议的人工步骤。

判定规则（按优先级）：

1. 任何参与方日志（含撕裂日志的可读前缀）存在 `APPLY(COMMIT)`，
   或协调者存在完整的 `DECISION(COMMIT)` → **FORCE COMMIT**。
   回滚已经提交的一方是不可能的，因此这是强制性结论。
2. 存在 `APPLY(ABORT)` 且无任何提交证据 → **FORCE ABORT**（已回滚方
   不可能再提交）。
3. 完整的 `DECISION(ABORT)` 且无冲突证据 → 重启协调者即可（幂等补发
   ABORT）。
4. 协调者日志完整但无决议、参与方仅 PREPARED → **推定中止**，直接重启
   协调者（恢复流程会持久化 ABORT）。
5. 协调者日志在可能的 `DECISION` 帧处撕裂、参与方仅 PREPARED →
   **AMBIGUOUS**：撕裂可能掩盖一条已 fsync 的 COMMIT，工具不会替人
   选择；必须联系每个参与方/资源属主，全部确认可提交后才允许人工
   force-commit，否则保持阻塞并从副本修复协调者。
6. 应到的参与方日志缺失/不可读 → **INSUFFICIENT EVIDENCE**：缺失方
   可能藏有 `APPLY(COMMIT)`，在证据补齐前禁止任何决议。

退出码：`0` = 结论安全可执行；`3` = 歧义/证据不足，必须人工处理。

## 3. 人工恢复操作守则（工具只给建议，不执行写入）

1. 先整体备份所有日志（含损坏文件），再做任何操作。
2. 运行 `inspect`（可加 `--json` 供工单系统归档证据）。
3. `FORCE COMMIT` / `FORCE ABORT`：按机构变更流程核对每个参与方资源状态，
   由 DBA/运维在双人复核下手工重建协调者 `DECISION` 记录（或通过管理端
   强制写入），再重启协调者；绝不能直接删除损坏帧后假装无事发生。
4. `AMBIGUOUS`：若任何一方无法确认，保持事务阻塞、冻结相关资源，先恢复
   协调者（副本/快照），由权威副本给出决议。
5. 恢复后再次运行 `inspect` 与 `selftest` 验证所有参与方状态一致、
   `blocked` 清单为空。

## 4. 示例

```
# 只读取证（文本报告，退出码 3 表示需要人工决策）
python3 -m two_phase_commit.cli inspect /var/tmp/tpc-run-42

# 机器可读证据
python3 -m two_phase_commit.cli inspect /var/tmp/tpc-run-42 --json
```
